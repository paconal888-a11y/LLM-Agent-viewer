# 관찰하면서 에이전트 사용법 익히기

앱의 **배우기** 화면에 저장 기록을 따라가는 14개 강의가 있습니다. 모델 없이 볼 수 있으니 먼저 강의를 끝내고, 이 문서로 직접 실행하며 확인하는 순서를 권합니다.

## 1. 모델과 도구 함수

계산 도구 예제를 먼저 실행하세요. `model.request`의 tools는 도구 설명이지 실행 결과가 아닙니다. `model.response`가 만든 이름·인자는 `tool.validate`를 거쳐 Python 함수에 전달됩니다. `tool.result`가 `role=tool` 메시지로 추가되고 다음 모델 호출에 들어갑니다.

도구 결과를 다음 입력에서 빼면 모델은 연산 결과를 받을 수 있을까요? 모델이 ‘계산했습니다’라고 말한 것과 실제 도구 호출 기록은 일치하나요?

실행 기록을 보고 작업 근거를 확인하세요. 도구 호출을 허용했다는 사실과 도구가 성공했다는 사실도 다릅니다.

## 2. 프로젝트 규칙 로딩

규칙 예제를 단계 정지로 실행하세요. `discover_rules → read_traced`의 호출 스택과 파일 경로를 확인합니다. `file.read`는 바이트, `file.decode`는 문자열, `rules.wrap`는 출처와 경계를 붙인 지침입니다. `context.assemble`에서 system 메시지에 들어갑니다.

AGENTS.md의 답변 언어 규칙을 바꾸고 저장한 뒤 새 대화에서 실행하세요. 다시 읽힌 원문과 조립한 messages를 먼저 확인하고 실제 응답을 평가합니다. 규칙을 끄면 어떤 파일 I/O가 사라지는지도 비교하세요.

규칙 파일을 만들었더라도 에이전트가 그 경로를 로드하는지 확인해야 합니다. 중요한 실행 제한은 자연어 지시만으로 강제할 수 없습니다.

## 3. 스킬 선택과 커맨드 확장

스킬 예제에서 Python은 검색을 위해 SKILL.md를 읽지만 모델에는 이름·설명 목록을 먼저 전달합니다. 모델의 load_skill 요청 후 본문을 전달합니다. 반면 `/summary ...`는 모델 호출 전에 입력 문자열을 프롬프트 템플릿으로 확장합니다.

스킬 설명은 선택을 돕고 본문은 실행 절차를 전달합니다. 둘을 구분해 작성하고 실제로 로드됐는지 확인하세요. 이 프로젝트의 /명령어는 셸 명령이 아닙니다.

## 4. 템플릿과 토큰화

`model.template → model.tokenize → model.detokenize`를 살펴보세요. messages는 역할과 도구를 가진 구조이며 템플릿이 특수 기호가 있는 문자열로 바꿉니다. tokenizer가 이를 ID로 변환합니다. UTF-8 바이트가 토큰 경계에 어떻게 나뉘는지 선택해 보세요.

지침·대화·도구 정의도 입력 한도를 차지합니다. 문자 수와 토큰 수가 같지 않습니다. 도구 결과를 무한히 추가하는 대신 필요한 내용을 담아야 합니다.

## 5. 생성 중 KV 캐시

교육용에서 `reference.forward.start`의 입력 길이를 확인하세요. 첫 forward는 새 입력 위치를 처리하고, 생성 중 KV를 사용하면 다음 forward는 직전에 선택한 한 토큰을 받습니다. 임베딩, Q/K/V projection, attention, cache.write, sample을 순서대로 펼쳐 보세요.

생성 중 KV 비교 실험은 A에서 전체 접두부를 반복 계산하고 B에서 저장한 K/V를 사용합니다. 두 실행의 생성 ID와 forward 입력 누적을 비교하세요. 요청 간 접두부 재사용 실험은 이전 요청과 같은 토큰 접두부를 재사용하는 별개 실험입니다.

이력을 줄이는 것, 입력 접두부를 안정적으로 유지하는 것, KV를 사용하는 것은 서로 다른 최적화입니다. 텍스트 기억을 삭제했다고 메모리의 KV가 모두 지워졌다고 단정할 수 없습니다.

## 6. 실행과 완료 조건

파일 수정 예제로 write_file → check_file → validation.final을 확인하세요. 모델이 답변을 만들었더라도 수정 파일 검사가 남아 있으면 하네스가 다시 검사를 요구합니다. 검사 실패·출력 한도·8회 호출 제한은 성공으로 표시하지 않습니다.

예제의 명시적 완료 조건도 확인하세요. 모델이 ‘수정했습니다’라고만 말해도 실제 write_file 결과가 없으면 `validation.requirements`가 반려하고 `context.repair`가 다음 입력에 부족한 행동을 추가합니다. 수정한 적이 없는 파일은 dirty 목록에도 없으므로, ‘수정 파일은 검사한다’라는 조건 하나로 요청한 쓰기의 실행 여부까지 보장할 수 없다는 차이를 살펴보세요. 자유 입력의 조건은 자동 추측하지 않습니다.

완료 조건을 명확히 정하고 실제 검증 도구를 연결하세요. 이 프로젝트의 구문 검사는 의미적 정확성이나 보안 검사를 대신하지 않습니다.

## 7. 다른 에이전트 분석

다른 에이전트의 문서와 실행 로그에서도 규칙 로딩 범위, 스킬 선택, 대화 요약과 이력 정책, 도구 공개·권한 검사, 완료 조건, MCP·LSP 연결을 살펴보세요. 각 항목이 어디에서 설정되고 어떤 입력과 실행을 바꾸는지 비교합니다. 실제 도구에서 확인하는 방법은 [실제 에이전트로 옮기기](TRANSFER.md)에 있습니다.

## 8. MCP·LSP 연결

MCP 계산 예제에서 별도 프로세스 → 발견 → 도구 목록 → schema → 모델 요청 → tools/call → 서버 결과 → tool 메시지를 확인하세요. 로컬 add_numbers와 같은 연산이더라도 프로토콜 왕복과 추가 입력이 생깁니다. 연결 전후 비교는 공개 도구 수·입력·시간·실제 호출을 보여줍니다.

LSP 진단 예제에서 문서 URI·버전과 실제 언어 서버 응답을 확인하세요. lsp_demo.py는 구문 검사를 통과하지만 정의되지 않은 missing_amount 진단이 있습니다. 프로토콜의 0부터 세는 좌표가 화면용 1부터 세는 행 번호로 바뀌는 과정도 확인하세요.

## 9. 피드백 저장과 재사용

보완이 발생한 요청을 완료한 뒤 같은 대화에서 다른 질문 두 개를 실행해 보세요. 원래 요청을 다시 실행하고 오류 · 기억 화면을 확인합니다. 최근 두 대화에서 빠진 지적이 저장 목록에는 남아 있는지, 실제 messages에 들어갔는지 대조하세요. 동일 요청 지적 재포함을 켠 뒤 다시 실행해 입력 변화를 확인합니다. 지적을 포함했어도 재발할 수 있으므로 실제 모델 행동을 따로 봅니다. 단순히 시간이 지났다는 이유로 원인을 단정하지 않습니다.

## 10. 계획 상태와 검증

계획·문서 검색 예제로 set_plan, search_text, complete_plan_step을 확인하세요. 검색은 실제 파일 I/O를 만들고 계획 도구는 상태 표를 바꿉니다. 계획의 체크와 작업 검증 게이트를 분리해 판단하는 연습입니다.

## 11. 모드·역할별 설정

같은 요청을 한 에이전트/집중 점검으로 비교하세요. 같은 가중치라도 점검 지시와 호출 예산이 바뀔 수 있습니다. 다음에는 하위 에이전트 실습에서 에이전트 선택별 첫 messages, 공개 도구, 실제 파일 읽기, queue/compute, join 뒤 주 모델의 입력을 대조하세요.

agents.json에서 하위 역할의 지침이나 도구 하나를 바꾸고 차이를 먼저 예측한 뒤 실행합니다. 주 세션의 과거 대화가 하위 입력에 통째로 전달되는지도 확인하세요. 자세한 경계는 [모드 설명](MODES.md)에 있습니다.

모드 이름만으로 더 강한 모델·병렬 추론·더 좋은 결과를 가정하지 않습니다. 변경한 입력·권한·비용과 실제 행동을 확인하세요.

## 12. 대화 요약과 원문 보관

대화 요약 예제의 **대화 저장소**에서 원문·세션 JSON·요약·실제 messages를 대조하세요. `ORBIT-731` 같은 값을 검색하고, 요약 생성용 model.request와 일반 답변용 model.request가 어떤 원문을 받았는지 확인합니다. 이어서 요약 재사용 예제를 열어 추가 요약 호출 없이 파일의 요약이 들어갔는지 봅니다.

저장된 원문, 현재 입력, 계산 상태인 KV는 서로 다릅니다. 요약에 빠진 내용은 원본이 디스크에 있어도 모델이 이번 입력에서 받지 못할 수 있습니다. [구현과 실습](MEMORY.md)에서 문자 기준과 토큰 한도의 차이도 확인하세요.

## 13. 고친 것이 실제로 나아졌는지 측정하기

한 번 잘 됐다고 개선이 아닙니다. 모델 출력은 확률적이어서 같은 조건에서도 결과가 달라집니다.

1. 실패한 실행의 단계 상세에서 **원인 찾기 → 원인 설명**을 엽니다. 실행기·설정, 도구·하네스, 모델 입력, 모델의 선택 중 어느 층을 먼저 볼지 확인합니다. 필수 도구가 공개되지 않았다면 모델을 탓할 수 없고, 입력에 없는 규칙은 모델이 따를 수 없습니다.
2. 입력란에 같은 요청과 완료 조건을 둡니다. 완료 조건이 없으면 코드가 통과를 판단하지 못하고 완료 상태만 셉니다.
3. **구성 · 비교**에서 `내 요청 · 스위치 하나만 바꾸기`를 고르고, 뒤집을 스위치와 반복 횟수를 정합니다. 규칙·스킬 파일이나 하네스 코드를 고친 경우에는 `바꾸지 않음 · 기준선 측정`으로 수정 전후를 각각 측정합니다.
4. 코드로 확인한 통과 수, 실패 층, 호출·토큰을 비교합니다. 회차가 적으면 차이가 우연일 수 있습니다.

회차마다 A·B 순서를 번갈아 바꾸고 seed를 1씩 늘리며 대화 이력을 분리합니다. 파일 쓰기를 허용한 회차는 끝날 때 작업 공간을 실행 전 상태로 되돌립니다. temperature가 0이면 seed를 바꿔도 같은 출력이 나올 수 있습니다. 이 통과율은 이 요청·이 조건의 관측값이며 일반적인 모델 성능이 아닙니다.
